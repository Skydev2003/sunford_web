# SUNFORD — แผนเปิดเว็บไซต์ 18 วันทำงาน

จัดทำ: 9 พฤศจิกายน 2026

สถานะ: แผนเสนอสำหรับติดตามงาน การจัดทำเอกสารนี้ไม่ได้เริ่มงานพัฒนาหรือสั่งเปิด Production

## เป้าหมายและสมมติฐาน

- เปิดเว็บแค็ตตาล็อกสินค้าจริงที่ลูกค้าดูข้อมูลและติดต่อฝ่ายขายได้ ตามขอบเขตที่ผู้ใช้ยืนยัน
- ทำงาน 6 วันต่อสัปดาห์ รวม 3 สัปดาห์ = 18 วันทำงาน ใช้วัน 1–18 เพราะยังไม่ได้ระบุวันเริ่มจริง
- วางแผนสำหรับผู้พัฒนาหลัก 1 คนก่อน โดยบริษัทส่งข้อมูลและตรวจรับควบคู่กัน เป็นสมมติฐานสำหรับจัดกำลัง ไม่ใช่ข้อมูลจำนวนทีมที่ยืนยันแล้ว
- วันแรกต้องเทียบปริมาณหน้าค้าง จำนวนสินค้าและข้อมูลที่ขาดกับกำลังจริง หากต้องกรอกข้อมูลจำนวนมาก ให้บริษัทช่วยเตรียมข้อมูลหรือปรับขอบเขตที่เปิดรอบแรกอย่างชัดเจน
- แต่ละวันช่วงวัน 1–15 แบ่งเวลาประมาณ 60% ทำงานหลัก 20% ทดสอบ/ตรวจงาน และ 20% แก้ปัญหา/ประสานงาน ไม่วางแผนจากการทำงานล่วงเวลา
- งานที่มีอยู่และผ่านการตรวจแล้วให้ตรวจยืนยันต่อยอด ไม่ทำซ้ำหรือออกแบบใหม่ทั้งหมด
- คงแนวทางเดิมของผู้ใช้: Week 1 เน้นโครงสร้าง/UX/ข้อมูล, Week 2 เน้น UI/Motion, Week 3 เน้นคุณภาพ/เปิดเว็บ/โดเมน โดยเริ่มงานเตรียมและทดสอบที่จำเป็นให้เร็วขึ้น

## ขอบเขตและความสำคัญ

**ต้องผ่านก่อนเปิดเว็บ:** รายการหน้าและสินค้าที่บริษัทตกลงเปิดรอบนี้ ข้อมูลถูกต้อง เส้นทางติดต่อฝ่ายขายครบ ใช้งานได้บนอุปกรณ์หลัก Privacy/Cookie ตามการใช้งานจริง SEO พื้นฐาน การตรวจรับ และความพร้อม Production

**เลื่อนได้เมื่อเวลาไม่พอ:** Motion ตกแต่งเพิ่มเติม ความสมบูรณ์ระดับทุกพิกเซลบนกรณีรอง เนื้อหาเสริมที่ไม่อยู่ในรายการเปิดรอบแรก และการปรับปรุงที่ไม่ขวางการใช้งานหลัก

ขอบเขตเปิดรอบนี้ไม่มีตะกร้าสินค้า ระบบสั่งซื้อ หรือชำระเงินออนไลน์ ไม่เพิ่มระบบหลังบ้าน ฟอร์ม หรือฟีเจอร์ใหม่โดยอัตโนมัติ หากพบความจำเป็นให้แยกเป็นข้อเสนอพร้อมขอบเขตและการอนุมัติ

## Checklist รายวัน

### Week 1 — โครงสร้าง UX และข้อมูลจริง

**วัน 1 — ล็อกสิ่งที่จะเปิดและสิ่งที่ยังขาด**

- [ ] ทำรายการทุกหน้า/ฟังก์ชันในรอบเปิดเว็บ ระบุเสร็จแล้ว/ต้องแก้/รอข้อมูล พร้อมประเมินปริมาณงานจริง
- [ ] แยกงานต้องผ่านก่อนเปิดกับงานเลื่อนได้ ระบุผู้รับผิดชอบและเกณฑ์จบของแต่ละงาน
- [ ] ขอรายชื่อสินค้าที่ขายจริง ข้อมูลโซลูชัน/บริการ นโยบาย ผู้ตรวจรับ และผู้ดูแลข้อมูลหลังเปิด
- [ ] ตรวจผู้ถือสิทธิ์ฐานข้อมูล Hosting โดเมน/DNS และอีเมลบริษัท ขอข้อมูลเครื่องมือวิเคราะห์/โฆษณาที่จะใช้

หลักฐานจบวัน: รายการเปิดรอบแรกและรายการรอข้อมูลที่มีเจ้าของ/กำหนดส่ง หากกำลังไม่พอให้ปรับงานเลื่อนได้ก่อน

**วัน 2 — เก็บ UX และโครงสร้างการนำทาง**

- [ ] ไล่เส้นทาง หน้าแรก → หมวด/หมวดย่อย → สินค้า → ติดต่อฝ่ายขาย รวมค้นหา/ตัวกรองที่อยู่ในขอบเขตเดิม
- [ ] ตรวจทุกเมนู Navbar และลิงก์ในหน้าให้ไปถูกปลายทาง ทั้งเมาส์ คีย์บอร์ด และมือถือ
- [ ] ทำรายการ URL ที่จะเปิดและ URL เก่าที่ต้องส่งต่อ โดยอ้างอิงเว็บเดิม/รายการที่ตรวจได้จริง
- [ ] สรุป UX ที่จำเป็นต้องแก้และยืนยันขอบเขตก่อนปรับส่วนร่วม ไม่เพิ่มฟังก์ชันจากข้อสันนิษฐาน

หลักฐานจบวัน: เส้นทางใช้งานและรายการแก้ UX ตรวจได้ครบ งานวัน 3–9 ใช้ข้อตกลงนี้เป็นฐาน

**วัน 3 — ยืนยันแหล่งข้อมูลสินค้าและการอ่านข้อมูล**

- [ ] ตรวจโค้ด API/Repository ที่มีอยู่และฐานข้อมูลที่บริษัทระบุ จับคู่รหัส รุ่น หมวด รูป สเปก และ URL
- [ ] ให้บริษัทรับรองเงื่อนไขสินค้าพร้อมจำหน่าย/เผยแพร่ และข้อมูลที่อนุญาตให้แสดงสาธารณะ
- [ ] ตรวจแยกข้อมูลทดสอบกับ Production และยืนยันว่ารอบทดสอบไม่เขียนข้อมูลจริงโดยไม่จำเป็น
- [ ] ทดลองอ่านข้อมูลจริงที่ได้รับอนุญาตและบันทึกตัวอย่าง/จำนวนที่ตรวจ โดยไม่เปิดเผยข้อมูลลับ

หลักฐานจบวัน: สัญญาข้อมูลและผลอ่านข้อมูลจริง ไม่ถือว่ามี Endpoint แล้วแปลว่าเชื่อมต่อและข้อมูลครบแล้ว

**วัน 4 — ปิดเส้นทางแค็ตตาล็อกและรายละเอียดสินค้า**

- [ ] เทียบสินค้าที่ต้องเปิดกับรายการจริง ตรวจชื่อ รุ่น รูป หมวด สเปก และรายละเอียดรายรุ่นที่มีข้อยกเว้น
- [ ] ตรวจว่าสินค้าที่ไม่เผยแพร่/ลบไม่ปรากฏ และข้อมูลจำลองไม่ทำให้ลูกค้าเข้าใจว่าเป็นสินค้าพร้อมจำหน่าย
- [ ] ยืนยันวิธีและระยะเวลาอัปเดตข้อมูล/Cache ทดสอบการแก้หรือซ่อนในข้อมูลทดสอบแล้วดูผลหน้าเว็บ
- [ ] ตรวจการเปิดตรง รีโหลด กลับหน้าก่อนหน้า ไม่มีสินค้า และกรณีโหลดข้อมูลไม่สำเร็จ

หลักฐานจบวัน: รายการตรวจเทียบสินค้าและข้อยกเว้นผ่าน พร้อมระบุข้อมูลที่ยังรอจากบริษัท

**วัน 5 — เติมเนื้อหาและเชื่อมช่องทางฝ่ายขาย**

- [ ] เติมโซลูชัน บริการหลังการขาย และหน้าในเมนูที่ค้างจากเนื้อหาที่บริษัทรับรอง
- [ ] ตรวจเงื่อนไขรับประกัน/บริการให้ตรงข้อเท็จจริง รวมข้อจำกัดที่ลูกค้าต้องทราบ ไม่ใส่บริการสอบเทียบเป็นบริการ SUNFORD
- [ ] ตรวจเบอร์โทร LINE อีเมล ที่อยู่ เวลาทำการ และผู้รับเรื่อง ให้ลูกค้าติดต่อพร้อมระบุรุ่นที่สนใจได้สะดวก
- [ ] สำรวจข้อมูลส่วนบุคคล คุกกี้ และบริการภายนอกจริง ส่งร่างข้อมูลสำหรับ Privacy/Cookie ให้บริษัทตรวจล่วงหน้าวัน 10

หลักฐานจบวัน: เนื้อหาหลักพร้อมตรวจรับ ช่องทางติดต่อยืนยันแล้ว และทราบเครื่องมือภายนอกที่ต้องพิจารณา

**วัน 6 — ตรวจรอบแรกและเตรียมทางเปิดเว็บ**

- [ ] ให้บริษัททดลองเส้นทางหลักและรับรองโครงสร้าง/ข้อมูล Week 1 จัดระดับข้อแก้ไขและกำหนดผู้ตอบข้อมูลค้าง
- [ ] ยืนยัน Preview ที่ใช้ตรวจรับและแยกฐานข้อมูล/ตัวแปรระบบจาก Production อย่างเหมาะสม
- [ ] ตรวจ Hosting โดเมน/DNS HTTPS ที่ต้องใช้ รายการ DNS อีเมลเดิม และขั้นตอนสลับโดยไม่กระทบอีเมล
- [ ] วัดความเร็วเบื้องต้นและเก็บภาพหน้าหลักก่อนเก็บ UI/Motion เพื่อใช้เปรียบเทียบ ไม่รอพบปัญหาใน Week 3

หลักฐานจบวัน: จุดตรวจ Week 1 ผ่าน หรือมีรายการสิ่งขวางที่ตกลงแก้ทันที ก่อนใช้งบเวลากับงานตกแต่ง

### Week 2 — UI ที่ครบ ใช้งานง่าย และ Motion ที่พอดี

**วัน 7 — เก็บ UI ส่วนร่วม**

- [ ] เก็บ Navbar/Footer/ปุ่ม/ตัวอักษร/ระยะห่างตามดีไซน์ที่อนุมัติ โดยแก้เฉพาะรายการที่ยังค้าง
- [ ] ตรวจมือถือ แท็บเล็ต และเดสก์ท็อป เมนูไม่ล้น ไม่บังเนื้อหา และปุ่มกดสะดวก
- [ ] ตรวจ Tab/Enter/Escape และจุดโฟกัสของเมนู/ปุ่มที่เกี่ยวข้อง
- [ ] ตรวจซ้ำหน้าแรก หน้าสินค้า และหน้าเนื้อหาตัวแทนหลังแก้ส่วนร่วม พร้อมภาพก่อน/หลัง

หลักฐานจบวัน: ส่วนร่วมสอดคล้องและไม่ทำให้หน้าอื่นที่เคยผ่านเสีย ไม่เปิดงานออกแบบส่วนร่วมใหม่โดยไม่มีขอบเขตอนุมัติ

**วัน 8 — เก็บ UI ของเส้นทางสินค้า**

- [ ] เก็บหน้ารวมสินค้า หมวด/หมวดย่อย และรายละเอียด โดยเริ่มจากหน้าที่ลูกค้าใช้เลือกสินค้าจริง
- [ ] ตรวจรูป อัตราส่วน ข้อความยาว ตารางสเปก และพื้นที่ปุ่มติดต่อบนจอแคบ
- [ ] ตรวจสถานะค้นหา/ตัวกรอง/ไม่มีข้อมูล/โหลดผิดพลาดตามฟังก์ชันเดิมที่อยู่ในรอบเปิด
- [ ] ทดสอบเส้นทางเลือกสินค้า → ดูรายละเอียด → ติดต่อฝ่ายขาย บนมือถือและคอมพิวเตอร์อีกครั้ง

หลักฐานจบวัน: หน้าสินค้าที่อยู่ในรายการเปิดรอบแรกใช้งานได้และข้อมูลไม่ถูก UI ตัดจนเข้าใจผิด

**วัน 9 — เก็บ UI ของหน้าเนื้อหาและติดต่อ**

- [ ] เก็บหน้าโซลูชัน บริการหลังการขาย และหน้าที่เหลือจากรายการวัน 1 โดยคงเนื้อหาที่บริษัทรับรอง
- [ ] ตรวจลำดับหัวข้อ ภาพ ข้อความ ลิงก์ และปุ่มติดต่อให้สอดคล้องกับหน้าสินค้า
- [ ] ตรวจการอ่าน ตัวอักษร/สี ภาพประกอบ และคีย์บอร์ดในส่วนที่แก้
- [ ] ให้บริษัทสรุปข้อแก้ไขเนื้อหาและส่ง Privacy/Cookie รวมรายชื่อผู้รับผิดชอบฉบับที่ใช้จริง เพื่อพร้อมทำวัน 10

หลักฐานจบวัน: หน้ารอบเปิดมี UI ครบ รายการเนื้อหายังไม่อนุมัติมีเจ้าของและกำหนดปิดก่อนวัน 12

**วัน 10 — Privacy/Cookie ตามข้อมูลและเครื่องมือจริง**

- [ ] จัดหน้าและลิงก์ Privacy Notice/Cookie ตามข้อมูลที่บริษัทตรวจรับ ระบุช่องทางติดต่อ ระยะเวลาเก็บ และผู้เกี่ยวข้องตามที่ใช้งานจริง
- [ ] หากมีตัวติดตามที่ต้องใช้ความยินยอม ให้ตรวจการรอก่อนโหลด การยอมรับ การปฏิเสธ และการเปลี่ยน/ถอนการเลือก
- [ ] ตรวจบริการฝังภายนอก เช่น วิดีโอ/แผนที่ และบันทึกวิธีจัดการที่บริษัทรับรอง ไม่สรุปจากชื่อโดเมนอย่างเดียว
- [ ] หากพบเพียงคุกกี้จำเป็น ให้บันทึกข้อสรุปจากการตรวจจริงและเลือกวิธีแจ้งที่เหมาะสม ไม่เพิ่มแบนเนอร์โดยไม่มีเหตุผล

หลักฐานจบวัน: เอกสารตรงพฤติกรรมจริง มีผลทดสอบกรณีที่เกี่ยวข้องและบริษัทรับรองเนื้อหา หากยังไม่พร้อมให้ใช้เวลางาน Motion วัน 11 มาปิดงานนี้ก่อน

**วัน 11 — เก็บ Motion/Animation ที่อยู่ในขอบเขต**

- [ ] เก็บเฉพาะรายการ Motion ที่ตกลงแล้ว เน้นการตอบสนองเมนู ปุ่ม และเนื้อหาที่ช่วยให้ใช้งานเข้าใจง่าย
- [ ] รักษา Motion และข้อยกเว้นหน้าแรกตามข้อตกลงที่มีอยู่ ไม่ย้ายทุก Prototype/Figma effect มาเว็บโดยอัตโนมัติ
- [ ] ตรวจ Reduced motion การคลิกระหว่างเคลื่อนไหว การเปลี่ยนหน้า และการกลับหน้าเดิมไม่ทำให้เนื้อหาหายหรือกดไม่ได้
- [ ] ตรวจความเร็วเทียบวัน 6 และการโหลดใหม่ใน Development/Production preview ไม่เพิ่ม Runtime/Hydration error

หลักฐานจบวัน: Motion ที่ต้องใช้ผ่านและไม่ทำให้เส้นทางขายช้าหรือเสีย ลูกเล่นเพิ่มเติมย้ายไปงานหลังเปิดทันทีเมื่อมีงานจำเป็นค้าง

**วัน 12 — SEO ตรวจรอบสอง และหยุดเพิ่มฟีเจอร์**

- [ ] ตรวจชื่อหน้า คำอธิบาย URL หลัก รูปเวลาแชร์ Sitemap/Robots และการตั้งค่าเก็บข้อมูลโดย Search engine ตามสภาพแวดล้อม
- [ ] ตรวจ Redirect จาก URL เดิมที่ต้องรองรับ ลิงก์ภายใน และ HTTP status ของหน้าไม่พบข้อมูล/URL ที่ไม่มีจริง
- [ ] ให้บริษัทตรวจ UI/เนื้อหาทั้งขอบเขต รับรองข้อความ/ภาพ/นโยบาย และสรุปรายการแก้ก่อนเปิด
- [ ] หยุดเพิ่มฟีเจอร์/เปลี่ยนดีไซน์หลังวันนี้ ใช้วัน 13–15 เพื่อแก้ปัญหาและตรวจรับ พร้อมส่งงานเสริมไปรอบถัดไป

หลักฐานจบวัน: จุดตรวจ Week 2 ผ่าน ฟังก์ชันและเนื้อหาพร้อมทดสอบเต็มรอบ ไม่มีการรอข้อมูลบังคับโดยไม่มีแผนแก้

### Week 3 — ตรวจคุณภาพ เปิดเว็บ และเผื่อปัญหา

**วัน 13 — ทดสอบเต็มเส้นทางและอุปกรณ์หลัก**

- [ ] ทดสอบเมนู หมวด ค้นหา/ตัวกรอง รายละเอียดสินค้า และโทร/LINE/อีเมล พร้อม URL ที่ลูกค้าเปิดตรงได้
- [ ] ตรวจอุปกรณ์/เบราว์เซอร์หลักที่บริษัทตกลง อย่างน้อยมือถือจริงที่หาได้และเดสก์ท็อป ระบุข้อจำกัดหากยืมอุปกรณ์ไม่ได้
- [ ] ตรวจคีย์บอร์ด โฟกัส Reduced motion รูปหาย ไม่มีข้อมูล ลิงก์เสีย และ Runtime/Hydration error ทั้ง Development กับ Production preview
- [ ] จัดรายการปัญหาเป็นขวางการเปิด/ต้องแก้/เลื่อนได้ พร้อมหลักฐาน Pass/Fail และผู้รับผิดชอบ

หลักฐานจบวัน: รายงานทดสอบที่ทำซ้ำได้ บั๊กเส้นทางขายและข้อมูลผิดได้รับลำดับก่อนงานตกแต่ง

**วัน 14 — Debug/Performance จากจุดที่วัดได้**

- [ ] วัดหน้าแรก หมวดสินค้า รายละเอียดสินค้า และหน้าเนื้อหาหนักบนเงื่อนไขอุปกรณ์/เครือข่ายที่บันทึกไว้
- [ ] แก้สาเหตุสำคัญที่พบจริง เช่น รูปใหญ่ JavaScript งานหนัก การอ่านข้อมูลซ้ำ หรือ Motion ที่ทำให้ตอบสนองช้า
- [ ] วัดซ้ำภายใต้เงื่อนไขเดิม ตรวจการกระโดดของหน้าและการตอบสนองระหว่างใช้งาน ไม่ดูเฉพาะคะแนนรวม
- [ ] ตรวจฟังก์ชันและภาพหลังแก้เพื่อกัน Regression สรุปข้อจำกัดที่ต้องติดตามจากผู้ใช้จริงหลังเปิด

หลักฐานจบวัน: ผลก่อน/หลังของคอขวดสำคัญและเส้นทางขายยังผ่าน ไม่ขยายเป็น Refactor เพื่อไล่คะแนนเต็ม

**วัน 15 — ตรวจรับสุดท้ายและยืนยันความพร้อม Release**

- [ ] ให้บริษัทตรวจรับฉบับที่จะเปิดจริง แก้และทดสอบซ้ำปัญหาขวางการเปิด รวมข้อมูลสินค้า/ช่องทางติดต่อ/นโยบาย
- [ ] ตรวจรายการก่อนเปิดท้ายเอกสาร บันทึกรุ่น/Commit ผลทดสอบ และผู้รับรอง เปิดได้เมื่อรายการบังคับผ่าน
- [ ] ยืนยัน Environment/ฐานข้อมูลจริง สิทธิ์สาธารณะ/ข้อมูลลับ สำรองข้อมูล และวิธีย้อนกลับทั้งตัวเว็บกับข้อมูลให้สอดคล้องกัน
- [ ] ตรวจ Release flow เดิมและความพร้อมโดเมน การสลับ DNS และอีเมลบริษัท ให้มีขั้นตอนและผู้ดำเนินการชัดเจน

หลักฐานจบวัน: บริษัทรับรองรุ่นปล่อยจริง ไม่มีปัญหาขวางการเปิด และผู้ดำเนินการพร้อม หากไม่ผ่านให้ใช้วันเผื่อโดยไม่ลดเกณฑ์รับงาน

**วัน 16 — เปิด Production และโดเมนจริง**

- [ ] ปล่อยรุ่นที่ตรวจผ่านตามขั้นตอน Production ของโปรเจกต์ และยืนยัน Deployment สำเร็จก่อนถือว่าเปิดแล้ว
- [ ] เชื่อม/สลับโดเมนตามค่าที่ผู้ให้บริการระบุจริง ตรวจ HTTPS และการส่งต่อโดเมนหลักที่ตกลง
- [ ] ทดสอบหน้าแรก แค็ตตาล็อก รายละเอียด ข้อมูลจริง โทร/LINE/อีเมล และนโยบายบนโดเมนจริงทั้งมือถือและคอมพิวเตอร์
- [ ] ตรวจว่า Search engine เข้าถึงหน้าสาธารณะตามที่ตั้งใจ ตรวจอีเมลบริษัท และเฝ้าดู Error หลังเปิดทันที

หลักฐานจบวัน: รุ่นที่ปล่อยและโดเมนตรงกัน เส้นทางขายทำงานและอีเมลเดิมไม่เสีย หากมีปัญหาร้ายแรงใช้แผนย้อนกลับที่ยืนยันไว้

**วัน 17 — เฝ้าดูและแก้ปัญหาหลังเปิด**

- [ ] ตรวจ Error การอ่านฐานข้อมูล รูป/หน้าโหลดล้มเหลว และความเร็วบนโดเมนจริง
- [ ] รับข้อสังเกตจากฝ่ายขาย/ผู้ตรวจรับ จัดระดับแล้วแก้สิ่งที่กระทบลูกค้าก่อน
- [ ] ทดสอบซ้ำเส้นทางที่ได้รับผลหลังทุกการแก้ ปล่อยแก้ผ่านขั้นตอนเดิม
- [ ] แยกคำขอฟีเจอร์และดีไซน์เพิ่มเติมออกจากบั๊ก ไม่ใช้วันเผื่อเพื่อเริ่มงานเสริม

หลักฐานจบวัน: ปัญหาที่กระทบการใช้งานหลักได้รับการแก้หรือมีข้อสรุป/ผู้รับผิดชอบชัดเจน

**วัน 18 — เวลาเผื่อ ตรวจปิดงาน และส่งมอบ**

- [ ] ใช้เวลาสำหรับปัญหาคงเหลือและทดสอบยืนยัน หากการเปิดต้องเลื่อน ให้ตรวจตามเกณฑ์เดิมและบันทึกเวลาติดตามหลังเปิดที่ยังต้องทำต่อ
- [ ] ส่งมอบวิธีดูแลข้อมูลสินค้า/เนื้อหาผ่านวิธีที่มีอยู่จริง คู่มือ Release และวิธีกู้คืน ไม่สร้างระบบจัดการใหม่เพิ่ม
- [ ] ระบุเจ้าของ Hosting/โดเมน/ฐานข้อมูล ผู้รับผิดชอบต่ออายุ ค่าใช้จ่าย ช่องทางแจ้งปัญหา และส่งสิทธิ์ผ่านช่องทางที่เหมาะสม
- [ ] ให้บริษัทรับมอบ พร้อมรายการงานเลื่อนได้ ผู้รับผิดชอบ และกำหนดพิจารณารอบถัดไป

หลักฐานจบวัน: บันทึกส่งมอบและรายการคงเหลือตรงกับสถานะจริง ไม่ถือว่าจบเพียงเพราะครบ 18 วัน

## งานที่ต้องผ่านก่อนเปิดเว็บ — ใช้ตรวจวัน 15–16

- [ ] รายการหน้า/ฟังก์ชันเปิดรอบแรกและผู้ตรวจรับได้รับการตกลง ไม่มียอดงานบังคับที่ยังไม่ระบุเจ้าของ
- [ ] สินค้าที่เปิดตรงกับรายการบริษัท รูป/รุ่น/สเปก/หมวดถูกต้อง และข้อมูลจำลองไม่ชวนให้เข้าใจผิด
- [ ] ยืนยันแหล่งข้อมูลจริง เงื่อนไขเผยแพร่ การอัปเดต/Cache และพฤติกรรมเมื่อไม่มีข้อมูลหรือข้อมูลล้มเหลว
- [ ] โซลูชัน บริการหลังการขาย ข้อมูลบริษัท/รับประกันได้รับการรับรอง ไม่มีคำอ้างบริการที่บริษัทไม่มี
- [ ] Navbar/ลิงก์/เส้นทางดูสินค้าและติดต่อฝ่ายขายผ่านครบ ช่องทางติดต่อและผู้รับเรื่องถูกต้อง
- [ ] หน้าในขอบเขตเปิดใช้ได้บนมือถือ/เดสก์ท็อปและเบราว์เซอร์หลักที่ตกลง รวมคีย์บอร์ดและ Reduced motion
- [ ] ไม่มีบั๊กขวางการใช้งานหลัก ข้อมูลผิดสำคัญ หรือ Runtime error ที่ทำให้เส้นทางหลักล้มเหลว
- [ ] Privacy/Cookie ตรงพฤติกรรมจริงและมีผลตรวจความยินยอมสำหรับเครื่องมือที่เกี่ยวข้อง
- [ ] SEO พื้นฐาน URL/Redirect และการอนุญาตให้เก็บข้อมูลบน Production ถูกต้อง หน้าที่ไม่ควรเปิดไม่เผยแพร่
- [ ] ความเร็วหน้าหลักผ่านเป้าหมายที่ตกลงจากการวัด ไม่เพิ่มปัญหาหลัง UI/Motion
- [ ] ตัวแปรระบบและสิทธิ์เข้าถึงเหมาะสม ไม่มีข้อมูลลับหรือข้อมูลภายในในผล API สาธารณะ/Browser
- [ ] สำรองข้อมูลและยืนยันวิธีย้อนกลับ มีผู้ดำเนินการและรุ่นที่ต้องย้อนกลับชัดเจน
- [ ] บริษัทรับรองรุ่นที่จะปล่อย พร้อมผลตรวจที่อ้างอิงรุ่นเดียวกัน
- [ ] หลังปล่อย: Production/โดเมน/HTTPS/ฐานข้อมูล/อีเมลและเส้นทางขายบนโดเมนจริงผ่าน พร้อมผู้เฝ้าดูหลังเปิด

## งานที่เลื่อนได้ — ย้ายออกก่อนเมื่องานบังคับเริ่มล่าช้า

- [ ] Motion ตกแต่งใหม่ Transition ซับซ้อน หรือเอฟเฟกต์จาก Prototype ที่ยังไม่ได้อนุมัติให้ขึ้นเว็บ
- [ ] การเก็บความต่างระดับพิกเซลบนกรณีรองที่ไม่กระทบการอ่าน การกด หรือแบรนด์หลัก
- [ ] เนื้อหาเสริม/บทความ/สื่อเพิ่มที่บริษัทไม่ได้กำหนดให้อยู่ในรายการเปิดรอบแรก
- [ ] เครื่องมือ Analytics/Marketing ใหม่และ Event เชิงลึกที่ยังไม่จำเป็นต่อเป้าหมายเปิดเว็บ หากบริษัทตกลงเลื่อนให้นำตัวติดตามออกจากรอบนี้อย่างชัดเจน
- [ ] การปรับ Performance เพิ่มหลังผ่านเป้าหมาย โดยเฉพาะการไล่คะแนนเต็มที่ยังไม่เห็นประโยชน์ต่อผู้ใช้
- [ ] การ Refactor เพิ่ม Dependency เปลี่ยน Stack หรือสร้างระบบจัดการที่อยู่นอกขอบเขต

ข้อจำกัด: ถ้าบริษัทตกลงว่างานใดจำเป็นก่อนเปิดแล้ว จะย้ายออกโดยฝ่ายเดียวไม่ได้ ปัญหาความถูกต้อง ความปลอดภัย หรือการติดต่อฝ่ายขายล้มเหลวไม่ใช่งานตกแต่งที่เลื่อนได้

## หมายเหตุการตรวจ Performance และ Release

- วัดตั้งแต่วัน 6 ตรวจผล Motion วัน 11 และแก้จริงวัน 14 เป้าหมายอ้างอิง Core Web Vitals คือ LCP ไม่เกิน 2.5 วินาที, INP ไม่เกิน 200 มิลลิวินาที และ CLS ไม่เกิน 0.1 โดยเป็นเป้าหมายข้อมูลผู้ใช้จริงที่ต้องติดตามหลังเปิดด้วย
- ก่อนเปิดใช้การวัดในสภาพทดสอบที่ทำซ้ำได้และทดสอบการตอบสนองจริง ไม่อ้างว่าข้อมูล Lab เป็นการผ่าน INP ของผู้ใช้จริงทั้งหมด หรือรอคะแนนเต็มจึงเปิด
- Release ใช้ [ขั้นตอนในโปรเจกต์](vercel.md): ทำจาก `uat` ที่ Commit แล้วและ Working tree สะอาดผ่าน `bun run deploy` ไม่ Push Production หรือใช้ Vercel CLI ลัดขั้นตอน
- `bun run deploy --check` เป็นการตรวจเงื่อนไขเบื้องต้น ไม่ใช่หลักฐานว่า Build/Tests ผ่านครบ การตรวจจริงต้องผ่าน Release flow ที่กำหนดและรอ Deployment สำเร็จ
- การย้อน Deployment ไม่ย้อน Migration/ข้อมูลอัตโนมัติ ต้องยืนยันแผนสำรอง/กู้ข้อมูลแยกกัน ไม่เพิ่มงานเปลี่ยน Schema ในแผนนี้โดยไม่จำเป็น
- รายการคำสั่งและ Release ในเอกสารเป็นงานตามแผนที่จะทำภายหลัง ไม่มีคำสั่ง Deploy หรือเปลี่ยน DNS ถูกรันระหว่างจัดทำแผนนี้
