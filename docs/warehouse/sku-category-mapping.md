# ตารางจับคู่ Warehouse SKU กับหมวดเว็บไซต์ SUNFORD

วันที่ตรวจ: 10 พฤศจิกายน 2026

ตารางนี้มี **380/380 SKU จาก API ที่ใช้งานจริง** เว็บไซต์ใช้รายการกลุ่ม G ที่จับคู่ได้ชัดเจน **89 SKU** และพัก **291 SKU** ตามคำสั่งผู้ใช้ เปิดสถานะเผยแพร่จริงพร้อมเหตุผลใน [runtime-product-status.csv](./runtime-product-status.csv) ส่วน [sku-category-mapping.csv](./sku-category-mapping.csv) และ [warehouse-product-mapping.json](../../src/features/catalog/data/warehouse-product-mapping.json) เก็บหลักฐานการจัดหมวดทั้งหมด

## แหล่งข้อมูลและสถานะล่าสุด

- เรียก `WAREHOUSE_API_URL` ที่ตั้งในเครื่อง + `/api/store/products` ได้ HTTP 200 และ JSON; `total_count = 380` และ `items.length = 380`
- ใช้ SKU ชื่อและหน่วยตรงตาม API ไม่มีการกรองสต็อกหรือกรองราคาเพิ่มในฝั่งตาราง
- ก่อนค่า env อัปเดต เคยอ่านฐาน Warehouse อย่างเดียวได้ 355 รายการที่ active/saleable/non-service; ในจำนวนนี้มี 267 SKU และชื่อตรงกับ API พอดี ใช้กลุ่มงานจากการอ่านนั้นเป็นหลักฐานประกอบเท่านั้น
- ตาราง **ยึดรายการจาก API 380 รายการ** แทนฉบับเตรียมจากฐานข้อมูล 355 รายการแล้ว API ไม่ส่ง company ID หรือ master item ID จึงไม่อนุมานตัวเลขเหล่านี้
- โดเมนสาธารณะ `https://www.sunford.co/api/store/products` ยังตอบ HTTP 404; การตรวจล่าสุดที่ผ่าน 200 ใช้ค่าจาก env ซึ่งอัปเดตภายหลัง ไม่ใช่การกล่าวว่า URL ที่ 404 ใช้ได้แล้ว
- ฐานเว็บไซต์ที่ตั้งในเครื่องล่าสุดผ่านการตรวจขั้นต่ำ `products.slug` และ `cms_documents` แล้ว ไม่ได้แก้ไฟล์ env โดย agent
- ไม่มีราคา ต้นทุน สต็อก รหัสผ่าน หรือ token ในไฟล์ตารางนี้

## กติกาหลักฐาน

1. ใช้หมวดหลักเดิม 5 หมวดและหมวดย่อยเดิม 23 หมวดจาก taxonomy ในเว็บไซต์
2. ชื่อที่ระบุ `Platform`, `Indicator`, เครื่องชั่ง อุปกรณ์ หรือระบบ POS ชัดเจน ใช้เป็นหลักฐานหมวดหลักก่อนกลุ่มงาน Warehouse เพราะกลุ่ม COMPONENT มีทั้งหัวอ่าน โครงสร้างแท่น และเครื่องชั่ง
3. รหัสรุ่นตรงกับรายการในหมวดย่อยเดิมจึงรับสมาชิกหมวดย่อยนั้น การเทียบไม่สนตัวพิมพ์ ช่องว่างและขีดคั่น แต่ไม่ตัด suffix ของรุ่น/ชุดอุปกรณ์เพื่อบังคับให้ตรงกัน
4. กลุ่ม CONSUMABLE ใช้หลักฐานสำหรับอุปกรณ์เสริม → วัสดุสิ้นเปลือง ชิ้นส่วนทั่วไปไม่ถูกอนุมานวัสดุ IP rating หรือระบบปฏิบัติการ
5. ชุด PACKAGED_PRODUCT ยังรอตรวจ ไม่ใช้ราคาชุดเครื่องพร้อมอุปกรณ์เป็นราคาหัวอ่านหรือแท่นเปล่า
6. บริการ/ขนส่ง สินค้า SAFETY รหัสภายในและชื่อ “ว่าง” ไม่ถือว่าเป็นสินค้าสำหรับเว็บไซต์ SUNFORD โดยอัตโนมัติ
7. `legacyProductCandidateIds` เป็นผู้สมัครเชื่อมเนื้อหาเดิม ต้องตรวจรุ่นย่อย จำนวนแพ็ก ปุ่ม หน้าจอและชุดอุปกรณ์ก่อนใช้เนื้อหาหรือเลือก canonical URL
8. หากรุ่นเดียวมีหลาย SKU จะมีหมายเหตุให้เลือก variant/ตัวแทนอย่างชัดเจน ไม่มีการยุบ SKU หรือเลือกตัวแรกเอง
9. “จับคู่หมวดและหมวดย่อยได้” เป็นสถานะด้านการจัดหมวด การเผยแพร่จริงต้องเป็นกลุ่ม G ไม่มีการชนกันของรุ่น/เนื้อหา และไม่ใช่เนื้อหาที่ CMS ซ่อนหรือลบไว้ ใช้ตารางนี้ฝั่งเซิร์ฟเวอร์เท่านั้น

หลักฐาน taxonomy มาจาก `scale-category-models.json`, `scale-subcategories.ts`, `indicator-subcategories.ts`, `platform-subcategories.ts`, `pos-subcategories.ts` และ `accessory-subcategories.ts` พร้อมรหัสรายการเนื้อหาที่ resolver คืนมา

## การใช้จริงทุกส่วน

ผู้ใช้ยืนยันแล้วให้ใช้รหัสขายกลุ่ม `G...` เป็นกลุ่มหลักบนเว็บและใบเสนอราคา ส่วนรหัสอื่นเป็น `review_alternative` ใน CSV/JSON กติกานี้ไม่ทำให้ค่าบริการ placeholder หรือสินค้านอกหมวดกลายเป็นสินค้าที่เผยแพร่ได้ และหากมีหลาย SKU กลุ่ม G สำหรับรุ่นเดียวกัน ยังต้องรักษา variant และแก้รายการซ้ำอย่างชัดเจนก่อนเลือก canonical URL หรือราคา

1. การเชื่อมต่อ API และ schema ขั้นต่ำของฐานเว็บผ่านแล้ว คู่มือตรวจซ้ำอยู่ใน [local-env-setup.md](./local-env-setup.md)
2. เปิด 89 SKU: เครื่องชั่ง 41, อินดิเคเตอร์ 6, โครงสร้างแท่น 21, POS 3 และอุปกรณ์เสริม 18 รายการ
3. พัก 291 SKU: นอกกลุ่ม G 147, กลุ่ม G ที่ยังไม่มีหมวด/หมวดย่อยครบ 113 และกลุ่ม G ที่ยังชนกันของรุ่น/เนื้อหา 31 รายการ การเพิ่มรายการเหล่านี้ภายหลังต้องมีหลักฐานการจับคู่เพิ่ม
4. Repository กลางใช้ข้อมูลจริงใน Home หมวด ลิงก์ ค้นหา เปรียบเทียบ จัดสเปคและใบเสนอราคาแล้ว ชุดเครื่องที่มีหัวอ่านรวมอยู่คิดราคาชุดครั้งเดียว ผลตรวจอยู่ใน [runtime-integration-delivery.md](./runtime-integration-delivery.md)
